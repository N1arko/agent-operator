# Инструкция агенту: внедрение workflow в существующий проект

## 1. Цель {#goal}

Подготовить проект к дальнейшей работе через общий канон, независимые `WI-NNN`, компактный `BOARD` и checkpoint-only `WAL`.

Adoption фиксирует фактический baseline и создаёт минимальный маршрут для следующей задачи. Массовое переписывание существующих документов и операционной истории не входит в обязательный результат.

## 2. Исследование {#research}

Изучи:
- инструкции и README проекта;
- существующие `specs/`, `BOARD`, `WAL`, roadmap и технические заметки;
- структуру кода, entrypoints и тесты;
- данные, API, UI, runtime, deployment и интеграции;
- существующие `@spec`.

Отделяй подтверждённое текущее состояние от будущих улучшений и вопросов для человека.

## 3. Установка модели {#install}

1. Добавь актуальные protocols, `SPEC-MAP.md` и `specs/work/README.md`.
2. Заполни `common/main.md` и `common/structure.md` по фактическому проекту.
3. Зарегистрируй действующие спеки в `SPEC-MAP.md` с краткой ответственностью.
4. Добавь `status` при создании или содержательном изменении спеки. Legacy-документ в `common/` или `modules/` без поля считается `active`.
5. Добавь `@spec` на затронутые точки ответственности; отдельная полная разметка всего legacy-кода оформляется WI, если она нужна.

## 4. Forward-only миграция {#migration}

Применяй новые правила ко всей новой работе:
- новый отслеживаемый item получает `WI-NNN` и файл в `specs/work/`;
- одна строка `BOARD` ссылается на один WI;
- новый WAL checkpoint появляется при незавершённой сессии или handoff;
- новый spec ID выбирается по актуальным правилам lifecycle и уникальности.

Legacy-состояние сохраняет валидность:
- строки `FEAT-*` и `INFRA-*` в `BOARD` можно завершить в прежнем формате;
- существующая секция `Completed` в WAL может жить до отдельной миграции;
- change-спеки `.A/.B/.C` сохраняют ID и ссылки;
- существующие спеки получают lifecycle по мере содержательных изменений.

## 5. Миграция roadmap {#roadmap}

Если `ROADMAP.md` использовался как каталог спек:
1. перенеси список действующих документов и их ответственность в `SPEC-MAP.md`;
2. перенеси полезные волны и устойчивые зависимости в одноимённые разделы карты;
3. сохрани уникальные сведения и backlinks;
4. оставь legacy-файл с короткой ссылкой на `SPEC-MAP.md` или удали его после решения человека.

## 6. BOARD и work items {#work}

Для будущей или порученной реализации:
1. создай один или несколько WI по `WORK-ITEM-PROTOCOL.md`;
2. укажи точные governing specs;
3. добавь компактные строки в `BOARD`;
4. начатую работу помести сразу в `In Progress`;
5. оставь WAL пустым до первого реального checkpoint.

Инвентаризация существующего канона сама по себе не создаёт WI для каждой спеки.

## 7. Завершение adoption {#done}

- `SPEC-MAP.md` даёт человеку обзор существующих спек и их ответственности;
- `structure.md` показывает modules, namespaces и code ownership;
- новые WI имеют отдельные файлы и строки `BOARD`;
- `WAL.md` содержит только актуальный handoff-контекст;
- legacy-идентификаторы и полезная история сохранены;
- открытые вопросы помечены `REVIEW`;
- в отчёте перечислены изменённые документы и оставшиеся решения.
