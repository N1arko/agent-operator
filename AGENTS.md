# Инструкции для Codex

## Старт каждой сессии

Первым действием полностью прочитать `specs/protocols/BOOT.md` и использовать
его как единый роутер к минимальному рабочему контексту. До первой правки
выбрать один маршрут: `first-spec-space`, `tracked-change`, `new-spec` или
`one-step-fix`. Локальная идентичность исполнителя хранится в `specs/.me` и не
коммитится.

## Цель проекта

Разработать Agent Operator — безопасный координатор сообщений и задач между
независимыми Codex-агентами на разных аккаунтах и компьютерах.

## Источники истины

Приоритет источников: инструкция пользователя → активные `specs/` → тесты →
код.

- `specs/common/` — общесистемный канон.
- `specs/modules/` — продуктовые, модульные и инфраструктурные спецификации.
- `specs/SPEC-MAP.md` — каталог действующего канона и его lifecycle.
- `specs/work/` — outcome, scope, acceptance и result конкретных `WI-NNN`.
- `specs/BOARD.md` — компактный статус, owner и blocker work items.
- `specs/WAL.md` — checkpoint только незавершённой работы.
- `specs/TECHDEBT.md` — осознанные технические компромиссы.
- `docs/adr/` — история существенных архитектурных решений.
- `docs/` — эксплуатационные инструкции, E2E-доказательства и исторический
  контекст.
- `KANBAN.md` — исторический журнал карточек до перехода на spec-driven
  workflow.

## Режим ведения проекта

Codex является основным исполнителем проекта и самостоятельно выполняет
исследование, проектирование, программирование, тестирование, документацию и
подготовку развёртывания. Участие пользователя требуется для предоставления
credentials, доступа к инфраструктуре, выбора бизнес-приоритетов и подтверждения
необратимых внешних действий.

Каждая новая рабочая сессия продолжает относящийся к ней `WI-NNN` из
`specs/BOARD.md`. Если активной работы нет, Codex разрешает governing spec через
`SPEC-MAP.md` и выбирает маршрут по `BOOT.md` до изменения spec-owned кода.

## Правила работы

1. Перед изменениями выполнить `specs/protocols/BOOT.md`.
2. Отслеживаемая работа получает файл `specs/work/WI-NNN-*.md` и одну строку в
   `BOARD.md`; legacy-строки сохраняются по forward-only migration.
3. В `BOARD.md` держать одну основную инженерную карточку в `In Progress`.
4. Для незавершённой карточки при handoff или паузе вести один checkpoint в
   `WAL.md`.
5. После завершения заполнить `Result`, архивировать WI, переместить строку в
   `Done` и удалить активный checkpoint. Управляющую спеку и её changelog
   менять только при реальном изменении канона.
6. Новый или существенно изменённый spec-owned код размечать полным
   `@spec spec://...#anchor` на точках ответственности.
7. Существенные технические решения фиксировать ADR и связывать с управляющей
   спекой.
8. Пользовательскую документацию вести на русском, код и технические
   идентификаторы — на английском.
9. Сохранять минималистичную модель данных: VPS работает как mailbox и
   presence-сервис для агентов.
10. OpenAI credentials и токены внешних сервисов сохранять на соответствующем
   host. Coordinator работает со своими device credentials.
11. Worker использует исходящее соединение к coordinator.
12. `agents_list` показывает зарегистрированных исполнителей, `agent_projects`
   показывает их локальные Codex-проекты. Список чатов через эти инструменты не
   публикуется.
13. `agent_start` создаёт свежий thread в явно выбранном проекте. Занятый агент
    сохраняет такой запуск в очереди.
14. `agent_send` с `replyTo` продолжает связанную сессию. Один агент выполняет
    один активный turn.
15. Worker автоматически выводит статус из событий app-server и отправляет
    итоговый ответ после `turn/completed`.
16. `codex app-server` запускается по запросу и останавливается после idle
    timeout. Worker остаётся постоянно доступным.
17. Файлы из репозиториев передавать ссылкой на commit, относительный путь и
    checksum. Локальные файлы передавать временным вложением с TTL.
18. Generic coordinator разворачивается из `deploy/self-hosted` на выбранном
    владельцем Docker host. Существующий private deployment сохраняется без
    изменений до отдельного migration/rollback действия.
19. Каждое сетевое изменение проектировать с idempotency, timeout, retry и audit.
20. Для новой функциональности добавлять тесты соответствующего уровня.
21. Перед завершением задачи запускать typecheck, lint и доступные тесты.
22. Инфраструктурные компоненты добавлять после появления подтверждённой
    потребности в текущем вертикальном сценарии.
23. Публичные инструкции поддерживать на английском и русском языках и
    проверять командой `pnpm docs:check`.
24. Приватные hostnames, IP-адреса, локальные пути и эксплуатационные evidence
    не включать в публичную поверхность репозитория и release assets.

## Стиль публичных текстов

Избегать формулировок-противопоставлений. Писать прямо, спокойно и предметно.
