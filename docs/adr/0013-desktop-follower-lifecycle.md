# ADR-0013: Handshake и жизненный цикл Desktop follower

Дата: 2026-07-28
Статус: принято

## Контекст

При первом удалённом turn новая задача успевала открыться в Codex Desktop с
пустой историей. Worker запускал turn через `thread-follower-start-turn`, после
чего сразу закрывал follower IPC-соединение и продолжал наблюдать завершение
через отдельный read-only app-server. История и результат сохранялись, а
открытый renderer иногда оставался в исходном состоянии `turnCount=0` до
перезапуска приложения.

Desktop считает renderer владельцем задачи и отдельно отслеживает подключённых
followers. Worker раньше не отправлял `thread-stream-following-changed`,
поэтому owner не регистрировал его и не публиковал исходный snapshot и patches.
Сохранение соединения до конца turn само по себе не заполнило пустую карточку.

## Решение

Перед открытием задачи worker отправляет `thread-stream-following-changed`
версии 1 с `following=true`. После открытия он ждёт snapshot owner и только
затем вызывает `thread-follower-start-turn`.

Follower IPC-соединение остаётся открытым до завершения внешнего наблюдателя
turn. После терминального результата worker вызывает
`thread-follower-load-complete-history`, чтобы owner перечитал сохранённые
turns, затем отправляет `following=false` и закрывает соединение.

Worker продолжает получать итоговый ответ через read-only app-server. Этот
канал отвечает за result coordinator, а follower-протокол синхронизирует
состояние открытого renderer.

## Последствия

- renderer регистрирует follower до запуска удалённого turn;
- запуск ожидает исходный snapshot и готовность owner;
- полная история перечитывается после сохранения терминального результата;
- prompt, прогресс и итоговый ответ отображаются без перезапуска Desktop;
- один активный turn удерживает одно локальное IPC-соединение;
- повторная ретрансляция `thread-stream-state-changed` не используется;
- регрессионные тесты проверяют handshake, загрузку истории и закрытие
  соединения после внешнего наблюдателя.
