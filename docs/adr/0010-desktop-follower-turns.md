# ADR-0010: запускать Windows-turn через Desktop follower IPC

- Статус: принято и подтверждено Windows E2E
- Дата: 2026-07-27

## Контекст

Отдельный `codex app-server` сохраняет turn в общей локальной истории.
Открытый ChatGPT/Codex Desktop не подписан на поток этого процесса. Broadcast
`query-cache-invalidate` успешно проходит через `\\.\pipe\codex-ipc`.
Внешний turn не добавляется в состояние уже открытой переписки.

Windows Desktop регистрирует в том же IPC команду
`thread-follower-start-turn`, версия `1`. Команда принимает ID переписки и
параметры нового turn. Выполнение запускает локальный host самого приложения,
поэтому renderer получает штатный поток `thread-stream-state-changed`.

## Решение

Worker `0.1.14` для продолжения существующей Windows-задачи:

1. подключается к `\\.\pipe\codex-ipc` и регистрирует внешний клиент;
2. открывает `codex://threads/<threadId>`;
3. отправляет request `thread-follower-start-turn`, версия `1`;
4. передаёт prompt в `turnStartParams.input`;
5. запускает read-only `thread/read` отдельного app-server до появления
   принятого `turnId` с терминальным статусом;
6. извлекает финальный `agentMessage`;
7. возвращает финальный `agentMessage` coordinator.

Проверка доступности Desktop выполняется до запуска turn. Если pipe
недоступен, worker использует отдельный app-server. После принятия
`thread-follower-start-turn` автоматический fallback не применяется, чтобы
исключить дублирование задачи.

`send-cli-request-for-host` остаётся внутренним renderer/Electron bridge и не
используется внешним worker. Это уточнение получено при read-only проверке
установленного Windows Desktop перед живым E2E.

Живой E2E `0.1.11` показал, что подключение внешнего клиента само по себе не
вызывает snapshot уже открытой задачи. Поэтому проверкой доступности служит
ответ владельца на `thread-follower-start-turn`. Ошибка до успешного ответа
разрешает fallback. После успешного ответа worker ждёт Desktop broadcast и не
создаёт второй turn.

Живой E2E `0.1.12` подтвердил штатное обновление renderer: prompt, прогресс и
финальный ответ появились без перезапуска Desktop. Форма полученных внешним
клиентом patches не позволила надёжно определить завершение. Чтение уже
сохранённого turn через отдельный app-server используется только для результата
coordinator и не меняет состояние интерфейса.

Живой E2E `0.1.13` выявил переходное состояние: отдельный app-server сразу
после Desktop-start возвращает для того же `turnId` пустой `failed`, пока ход
продолжается в приложении. После завершения `thread/read` возвращает
`completed` и финальный `agentMessage`. Worker продолжает опрос после
переходного failed. Ограничение для настоящего зависшего или ошибочного хода
закрывает lease из AOP-075.

Итоговый E2E `0.1.14` подтвердил короткий turn за `9,544 ms`, длинный turn за
`47,860 ms` и параллельный сценарий за `75,968 ms`. Каждый request создал один
пользовательский turn, один финальный ответ и один completed-result.
Отдельная пользовательская задача завершилась во время параллельного
remote-turn. Полный протокол сохранён в
`docs/E2E_WINDOWS_DESKTOP_0.1.14.md`.

## Последствия

Prompt, прогресс и итоговый ответ формируются тем же host, который обслуживает
открытый интерфейс. Worker продолжает публиковать собственный heartbeat и
итоговый result. Активный Desktop-turn пока ставит последующие сообщения в
очередь; отдельная управляемая отмена остаётся в AOP-075.

Создание новой проектной задачи пока использует app-server. Расширение
командного IPC на `start-conversation` и проверка macOS ведутся в AOP-076.
