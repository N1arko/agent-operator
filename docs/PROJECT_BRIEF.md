# Концепция Agent Operator

## 1. Замысел

Agent Operator позволяет независимым Codex-агентам на Mac, Windows и других
компьютерах общаться друг с другом.

Один агент может:

- увидеть другого агента и его состояние;
- узнать, чем тот сейчас занят;
- посмотреть доступные локальные проекты;
- запустить свежую работу в выбранном проекте;
- передать информацию в текущую работу;
- дождаться обновления;
- получить итоговый ответ и созданные файлы.

Модель взаимодействия повторяет привычную работу с сабагентами: presence,
mailbox, запуск, сообщение, ожидание и автоматический возврат результата.

## 2. Основной сценарий

```text
Windows Codex
  → проверяет состояние Mac Codex
  → смотрит проекты Mac Codex
  → запускает свежую работу в выбранном проекте
  → периодически смотрит статус или ждёт обновление
  → получает итоговый ответ
  → готовит свой план
  → отправляет Mac Codex запрос на проверку
  → получает замечания
  → выполняет локальную работу на Windows
```

Агенты сохраняют собственные локальные контексты и Codex-сессии. Coordinator
маршрутизирует сообщения и сообщает об их состоянии.

## 3. Границы системы

Coordinator на VPS хранит:

- зарегистрированных агентов;
- online, idle, busy и offline состояние;
- краткое описание текущей активности;
- очередь сообщений;
- связь ответа с исходным сообщением;
- краткие дескрипторы локальных проектов;
- временные файлы с ограниченным сроком хранения.

Worker на компьютере:

- поддерживает исходящее соединение с VPS;
- управляет локальным `codex app-server`;
- знает локальный `threadId`;
- получает список локальных Codex-проектов;
- разрешает выбранный `projectId` в primary folder и дополнительные roots;
- доставляет связанные сообщения в активную сессию;
- запускает новую работу после освобождения агента;
- автоматически отправляет финальный ответ.

Coordinator не хранит локальные пути, содержимое проектов и OpenAI credentials.

## 4. Agent

```json
{
  "id": "mac-codex",
  "name": "Codex на Mac",
  "status": "busy",
  "currentProject": {
    "id": "project_agent_operator",
    "displayName": "Agent Operator",
    "availability": "available"
  },
  "currentActivity": "Изучаю структуру папок с проектами",
  "activeRequestId": "msg_123",
  "lastSeenAt": "2026-07-25T19:10:00Z"
}
```

Состояние выводится worker автоматически:

```text
worker heartbeat отсутствует → offline
worker доступен, turn отсутствует → idle
turn/started → busy
turn/completed → idle
```

`currentActivity` строится из входящего запроса и последних безопасных событий
app-server. Агенту не требуется вручную вести статус.

`currentProject` является информационным полем. Путь остаётся на локальном
компьютере.

`agents_list` показывает зарегистрированных worker-агентов и их состояние. Он
не возвращает историю чатов. Проекты выбранного агента возвращает
`agent_projects`.

## 5. Project descriptor

```json
{
  "id": "project_agent_operator",
  "displayName": "Agent Operator",
  "availability": "available",
  "primaryFolderName": "agent-operator",
  "additionalFolderCount": 0
}
```

Worker является источником project descriptor. Coordinator хранит только
непрозрачный `projectId`, отображаемое название и availability. Абсолютные пути
остаются локальными.

Публичная документация Codex пока не гарантирует внешний стабильный API
идентификаторов локальных проектов. В техническом эксперименте проверяется
app-server и локальная модель проектов. При отсутствии подходящего API worker
использует собственные непрозрачные ID и локальное сопоставление.

## 6. Message

```json
{
  "id": "msg_123",
  "from": "windows-codex",
  "to": "mac-codex",
  "kind": "request",
  "body": "Посмотри, как организованы проекты на Mac.",
  "projectId": "project_agent_operator",
  "projectName": "Agent Operator",
  "replyTo": null,
  "deliveryMode": "start",
  "status": "queued",
  "attachments": [],
  "createdAt": "2026-07-25T19:05:00Z"
}
```

Типы сообщений MVP:

- `request` — новая работа;
- `message` — информация в текущую работу;
- `update` — промежуточный ответ;
- `question` — уточнение;
- `result` — итоговый ответ;
- `error` — выполнение завершилось ошибкой.

`replyTo` связывает уточнение, дополнительную информацию и результат с исходным
запросом. Отдельная сущность задачи для этого не используется.

Статусы доставки:

```text
queued → delivered → completed
                  ↘ failed
```

## 7. Режимы доставки

### `agent_send`

Передаёт информацию в текущую работу. Сообщение содержит `replyTo` активного
запроса. Worker доставляет его в связанную Codex-сессию на безопасной границе.

### `agent_start`

Создаёт новый корневой запрос в выбранном проекте:

- свободный агент создаёт свежий thread;
- занятый агент сохраняет запуск в очереди;
- после завершения текущего turn worker запускает следующую работу;
- primary folder проекта становится `cwd`;
- дополнительные папки проекта становятся workspace roots.

Новая просьба не заменяет активную сессию.

### `agent_threads`

Ставит worker ограниченный запрос поиска недавних локальных задач. Worker
читает индекс Codex state DB, возвращает до 20 кратких записей и сохраняет
локальные пути на своём компьютере.

### `agent_thread_send`

Начинает новый turn в существующей задаче по точному `threadId`. Сопоставление
с опубликованным проектом является опциональным. Активная задача сообщает
отправителю, что её текущий turn ещё выполняется.

Worker открывает создаваемую или продолжаемую задачу в ChatGPT Desktop
принимающего компьютера. Новая задача получает заголовок `[Agent Operator] …`.
Итоговый result содержит её технический `threadId`.

Turn запускается до открытия deep link. Worker сохраняет принятый запрос в
общем state file, поэтому обновление версии и перезапуск процесса продолжают
локальную очередь. Coordinator ограничивает backlog тремя незавершёнными
запросами.

### `agent_wait`

Ждёт новое сообщение или изменение статуса после заданного cursor. Ожидание
имеет ограниченный timeout и может повторяться.

## 8. Автоматический результат

Worker связывает входящий `messageId` с локальным `threadId`.

```text
agent_start получен
  → worker разрешает projectId
  → worker запускает Codex
  → worker создаёт свежий thread
  → app-server сообщает turn/started
  → worker публикует busy
  → app-server сообщает item/completed с финальным agentMessage
  → app-server сообщает turn/completed
  → worker выбирает финальное сообщение завершённого turn
  → coordinator получает result с replyTo=requestMessageId
  → автор запроса получает результат
```

`agent_send` с `replyTo` на корневой запрос продолжает соответствующий thread.
Codex может самостоятельно отправить `update`, `question` или новый
`agent_start` другому агенту через MCP. Итоговый `result` worker отправляет
автоматически.

## 9. Передача файлов

### Файл в общем Git-репозитории

Отправитель передаёт ссылку:

```json
{
  "type": "git_file",
  "repository": "git@github.com:example/project.git",
  "revision": "a12bc34d",
  "path": "docs/migration-plan.md",
  "sha256": "..."
}
```

Получатель сопоставляет repository с remote выбранного локального проекта,
проверяет commit, path и SHA-256. Fetch выполняется при отсутствии commit в
локальной object database. Файл читается через `git show` без переключения
активной ветки. Применение commit остаётся отдельным локальным действием.

### Локальный файл

Worker загружает файл во временную папку coordinator:

```json
{
  "kind": "temporary_file",
  "fileId": "file_4821",
  "name": "migration-plan.xlsx",
  "size": 48231,
  "sha256": "...",
  "expiresAt": "2026-07-28T12:00:00Z"
}
```

Получающий worker скачивает файл во временный локальный каталог и проверяет
checksum. Файл не записывается в рабочий проект автоматически.

S3 для MVP не используется. Coordinator хранит небольшие временные файлы на
локальном диске VPS и удаляет их после TTL.

## 10. MCP-инструменты

```text
agents_list
agent_status
agent_projects
agent_start
agent_threads
agent_thread_send
agent_send
agent_wait
```

`agents_list` показывает только агентов и состояние. `agent_projects`
возвращает проекты конкретного агента. `agent_start` создаёт свежий thread в
выбранном проекте. `agent_threads` выполняет bounded-поиск в локальном индексе.
`agent_thread_send` продолжает задачу по точному ID. `agent_send` продолжает
связанную работу по `replyTo`.

## 11. Ресурсная модель

Worker работает постоянно и большую часть времени ожидает long polling.

`codex app-server`:

- запускается при входящем запросе;
- остаётся активным на короткий idle timeout;
- завершается при отсутствии работы;
- запускается повторно для следующего запроса;
- возобновляет локальный thread через `thread/resume`.

В ожидании модель не вызывается и токены Codex не расходуются. Точная память и
CPU измеряются в первом техническом эксперименте.

Начальная конфигурация:

```text
active turns per agent: 1
app-server idle timeout: 5 minutes
worker polling: long polling
file transfer: explicit
thread search: state DB only, limit 20
```

## 12. Объём MVP

- coordinator с SQLite;
- worker на macOS и Windows;
- регистрация агента по token;
- presence и heartbeat;
- `idle`, `busy`, `offline`;
- краткая текущая активность;
- список локальных Codex-проектов;
- ограниченный поиск локальных задач;
- продолжение существующей задачи по точному ID;
- видимый запуск удалённой задачи в ChatGPT Desktop;
- запуск свежего thread в выбранном проекте;
- durable mailbox;
- связанные сообщения через `replyTo`;
- один активный turn;
- очередь новых запусков;
- безопасная доставка сообщения в текущую работу;
- cursor-based ожидание;
- автоматический возврат результата;
- Git file reference;
- небольшое временное вложение;
- ленивый запуск app-server;
- восстановление после перезапуска.

## 13. Критерии успеха

MVP готов, когда:

1. Два Codex с разными аккаунтами видят друг друга.
2. Один агент получает достоверный статус другого.
3. `agents_list` не раскрывает историю чатов.
4. `agent_projects` возвращает доступные локальные проекты.
5. `agent_start` запускает свежий thread в выбранном проекте.
6. Новый запуск ждёт завершения занятого агента.
7. Связанное сообщение попадает в нужный thread.
8. После завершения результат автоматически возвращается отправителю.
9. `agent_wait` получает результат без постоянного частого polling.
10. Git-файл читается вторым агентом по commit.
11. Временный файл передаётся с проверкой checksum и удалением по TTL.
12. Перезапуск worker сохраняет очередь и локальный thread.
13. Поиск задач использует state DB и возвращает не более 20 записей.
14. Измерена нагрузка worker и app-server в idle и active режимах.

## 14. Отложенное развитие

- крупные файлы и S3;
