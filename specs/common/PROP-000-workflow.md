# PROP-000: Фундаментальные решения проекта {#root}

## Простыми словами {#plain-language}

Этот документ фиксирует правила, которые действуют во всём проекте. Здесь описывается, как принимать решения, как связывать спеки с кодом, как проверять готовность и как оставлять вопросы так, чтобы следующий человек или агент понял состояние проекта.

## 1. Назначение {#goal}

- Задать общий порядок работы по spec-driven модели.
- Зафиксировать минимальные правила качества, тестирования и handoff.
- Установить приоритеты: человек задаёт намерение, спека фиксирует канон, тесты проверяют канон, код реализует канон.
- Зафиксировать обязательную трассировку кода через `@spec`.

## 2. Границы документа {#scope}

### 2.1. Входит {#scope.in}

- правила работы со спеками;
- правила `BOARD.md`, `WAL.md`, `TECHDEBT.md` на уровне проекта;
- обязательная связь кода с управляющими спеками;
- базовые ожидания к тестам, проверкам и отчёту;
- порядок фиксации спорных мест.

## 3. Базовые правила workflow {#workflow}

- `SPEC-MAP.md` служит человекочитаемым каталогом канона и ответственности спек.
- Спецификация хранит долговечное поведение, контракт или инвариант.
- `WI-NNN` хранит outcome, scope, acceptance и result конкретного прохода реализации.
- `BOARD.md` хранит статус, owner, priority и blocker work items.
- `WAL.md` получает checkpoint, когда незавершённую работу нужно продолжить или передать.
- Перед первой правкой агент выбирает один маршрут: `first-spec-space`, `tracked-change`, `new-spec` или `one-step-fix`.
- Пустой шаблон и starter draft не считаются содержательным продуктовым каноном. Первая реализация продукта начинается после создания первого spec-space и WI.
- Реализация поведения, уже полностью описанного активной спекой, получает WI с `Canon action: none` и не меняет текст спеки или changelog без найденного пробела канона.
- Мелкое исправление может пройти без WI, `BOARD` и `WAL`, когда уже существуют код и ясная active spec, а работа не имеет отдельного результата, критериев, риска, зависимости, статуса или продолжения.
- Одна спецификация может реализовываться несколькими WI; один WI может объединять несколько спек для одного атомарного результата.
- Каждый spec ID и WI ID уникален в своём namespace и не переиспользуется.
- Перед работой агент читает `AGENTS.md`, `BOOT.md`, найденный WI и минимальный набор управляющих спек.
- Новая спека регистрируется в `SPEC-MAP.md`; `structure.md` меняется только вместе с технической топологией проекта.
- Осознанный компромисс фиксируется в `TECHDEBT.md`, спорное место канона — через `REVIEW`.
- В `In Progress` находится одна основная инженерная карточка Agent Operator.
- Существенное архитектурное решение получает ADR.
- Пользовательская документация ведётся на русском; для публичного open-source
  релиза допускается синхронная английская версия. Код и технические
  идентификаторы ведутся на английском.

## 4. Трассировка кода {#traceability}

Spec-owned код — это код, конфигурация, миграция, worker, materializer или UI-компонент, который реализует поведение, контракт или инвариант из `specs/`.

Новый или существенно изменённый spec-owned код получает маркер `@spec` с полным адресом:

```ts
/**
 * @spec spec://modules/core/FEAT-010-account-lifecycle#api.create
 * @spec spec://common/PROP-006-API#errors
 */
```

Маркеры ставятся на точках ответственности:
- файл, если он почти целиком принадлежит одной спеке;
- обработчик;
- сервис или класс;
- крупный UI-компонент;
- worker или job processor;
- миграция;
- materializer, read-model builder или импортёр данных.

В коде указываются актуальные управляющие спеки. История смены поведения живёт в самих спеках.

## 5. Проверки и качество {#quality}

Для каждого WI нужно определить:
- какие тесты или ручные проверки подтверждают готовность;
- какие части поведения проверяются автоматически;
- какие риски остаются за границей текущей работы;
- какие `@spec`-адреса должны находиться поиском по коду.

Если в проекте есть `tools/spec-lint`, он должен проверять:
- существование файла для каждого `spec://`;
- наличие якоря в документе;
- отсутствие дублей `TYPE-NNN` среди активных `PROP`, `FEAT` и `INFRA`;
- корректность `@spec`-маркеров.

Строго валидируются активные `specs/common/*.md`, `specs/modules/**/*.md`, `SPEC-MAP.md`, `specs/work/**/*.md`, `BOARD.md`, `WAL.md`, `TECHDEBT.md`, `structure.md` и код. Обучающие зоны `.human/`, `specs/examples/`, `specs/protocols/`, fenced code blocks, HTML-комментарии с примерами и placeholder `spec://...` не считаются реальными ссылками.

В `structure.md#code-map` разрешены namespace patterns вроде `spec://modules/core/*`. Они используются только как карта ownership для папок кода. В `@spec`, WI, `TECHDEBT.md` и рабочих спеках используются полные адреса с `#anchor`; `BOARD.md` показывает компактные spec IDs, `WAL.md` ссылается на WI.

Строки `structure.md#modules.index` со статусом `template` считаются
starter-заготовками до первой рабочей регистрации. Перед первой реальной
работой они должны быть заполнены, переименованы или удалены.

Перед завершением инженерного WI Agent Operator выполняются `pnpm typecheck`,
`pnpm lint` и `pnpm test`; рискованные release-изменения дополняются живым E2E
на exact revision.

## 6. Чеклист заполнения {#checklist}

- [ ] Название проекта и назначение заполнены в `main.md`.
- [ ] Модули проекта перечислены в `structure.md`.
- [ ] Нет дублей `TYPE-NNN` среди активных спек.
- [ ] Стартовые `PROP-*` отражают фактические решения проекта.
- [ ] `SPEC-MAP.md` отражает действующие и draft-спеки.
- [ ] Отслеживаемая работа имеет файл WI и одну строку в `BOARD.md`.
- [ ] `WAL.md` содержит только актуальные checkpoints незавершённой работы.
- [ ] В инструкциях проекта есть правило `@spec`.
- [ ] До первой правки выбирается один из четырёх маршрутов, а шаблонный канон не принимается за рабочий.
- [ ] Уже описанное поведение реализуется через WI с `Canon action: none` без лишнего изменения спеки.
- [ ] Спорные места помечены `REVIEW`, а компромиссы вынесены в `TECHDEBT.md`.
